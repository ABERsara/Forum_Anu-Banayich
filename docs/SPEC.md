## 1. סקירה כללית

### 1.1 מטרת המערכת

עמותת "אנו בניך" מבקשת לפתח פלטפורמה דיגיטלית מאובטחת המשמשת כמרחב תמיכה, קהילה, פורום וייעוץ מקצועי לאוכלוסיות שכול: אלמנים, אלמנות, יתומים ויתומות. המערכת מיועדת לשמש מרחב בטוח, מוגן ומכובד, תוך שמירה קפדנית על פרטיות המשתמשים, כבודם ורגישותם התרבותית-דתית.

### 1.2 עקרונות יסוד

- **פרטיות כברירת מחדל** — כל מידע אישי ומסמכים רגישים מוצפנים ומוגנים
- **רגישות תרבותית-דתית** — הפרדה ברורה בין מגזרים (חסידי, ליטאי, ספרדי, כללי)
- **הפרדה בין קבוצות** — אלמנים, אלמנות, יתומים ויתומות אינם רואים תוכן שאינו שייך לקבוצתם
- **אימות קפדני** — כניסה למערכת מותנית באישור שני מנהלים ובמסמכים מאמתים
- **מרחב מוגן** — מנגנון דיווח, מעקב והסתרה אוטומטית של תוכן שאינו הולם
- **שקיפות פנימית** — Audit Trail מלא לכל פעולה מנהלתית ורגישה
- **רב-לשוניות** — ארכיטקטורת i18n מובנית; עברית + אנגלית בהשקה; ניתן להוסיף שפות נוספות ללא שכתוב

### 1.3 קהל יעד

| מי שאיבד בת זוג | מי שאיבדה בן זוג | מי שאיבד הורה | מי שאיבדה הורה |

## 2. ERD — ישויות ומבנה נתונים

### 2.1 ישויות ראשיות

#### User (משתמש)

שדות: UUID, שם פרטי, שם משפחה, ת"ז/מספר דרכון (מוצפן), מייל (מוצפן), טלפון (מוצפן), תמונת זיהוי (URL מאובטח), סוג משתמש `[אלמן|אלמנה|יתום|יתומה]`, מגזר `[חסידי|ליטאי|ספרדי|כללי]`, סטטוס חשבון `[ממתין_לאימות|ממתין_לאישור|אושר_חלקית|פעיל|נדחה|מושעה|מבוטל]`, תאריך לידה, תאריך יצירה, תאריך אישור, מזהה מאשר ראשון, מזהה מאשר שני, `sla_escalation_sent_at`.

> **הקצאת תא:** שדה `מגזר` אינו בחירה עצמאית של המשתמש — המנהל מקצה אותו לתא הסופי (קבוצה + מגזר) בעת בחינת הבקשה, על בסיס מסמכי ההרשמה ושאלות זיהוי השיוך.

> **שדה עתידי (ספרינט 4):** `google_uid` (nullable) — יתווסף עם יישום Google OAuth. מאפשר כניסה חוזרת דרך גוגל לאחר הרשמה מלאה ואישור בלבד.

> **שינוי v1 → v2:** "תמונת פנים" שונה ל-"תמונת זיהוי" (ניסוח רגיש יותר, אותה פונקציונליות).

#### Admin (מנהל)

שדות: מזהה, שם, אחריות מגזרים (רשימה), אחריות קבוצות (רשימה), הרשאות מיוחדות, תאריך מינוי.

#### Moderator (מבקר)

שדות: מזהה, שם, מגזרים אחראיים (רשימה), קבוצות אחראיות (רשימה), מייל התראות.

#### Professional (איש מקצוע)

שדות: מזהה, שם, תחום `[עו"ד|רואה חשבון|פסיכולוג|יועץ כלכלי|רב/דיין|רפואה|סוציאל וורקר|אחר]`, מגזרים משויכים (רשימה, ניתן לסמן "הכל"), קבוצות משויכות (רשימה, ניתן לסמן "הכל"), מייל, טלפון, תיאור קצר, פעיל (boolean).

#### ForumPost (הודעת פורום)

שדות: מזהה, מזהה יוצר, סוג הפצה `[תא|קבוצה|מגזר|כולם]`, קבוצת יעד, מגזר יעד, כותרת, תוכן (מוצפן), תאריך יצירה, תאריך עריכה, מספר דיווחים, סטטוס `[גלוי|מוסתר|מחוק]`.

#### DirectMessage (הודעה פרטית)

שדות: מזהה, מזהה שולח, מזהה מקבל, תוכן (מוצפן), תאריך, קרוא (boolean).

#### ProfessionalQuery (שאלה מקצועית)

שדות: מזהה, מזהה שואל, מזהה איש מקצוע (אופציונלי — לשאלה ספציפית), תחום (לשאלה כללית), תוכן (מוצפן), ציבורי (boolean), תשובה (מוצפן, אופציונלי), תאריך שאלה, תאריך תשובה, סטטוס `[פתוח|נענה|סגור]`.

#### Report (דיווח)

שדות: מזהה, מזהה מדווח, מזהה מדווח-עליו, סוג יעד `[הודעת_פורום|הודעה_פרטית|שאלה_מקצועית]`, מזהה יעד, סיבה (טקסט חופשי), תאריך, החלטה `[ממתין|שגוי|מוצדק]`, מזהה מבקר מטפל, תאריך החלטה.

#### Document (מסמך)

שדות: מזהה, מזהה משתמש, סוג `[תעודת_פטירה|תמונת_זיהוי|ת"ז|דרכון]`, URL (מוצפן), hash, תאריך העלאה, תוקף (אופציונלי).

#### AuditLog (לוג פעולות)

שדות: מזהה, מזהה משתמש מבצע, סוג פעולה, ישות מושפעת, מזהה ישות, timestamp, IP מקור (מוצפן), פרטים (JSON).

### 2.2 קשרים בין ישויות

| ישות A | ישות B | קשר | הערות |
|---|---|---|---|
| User | Group/Sector | many-to-many | תוכן גלוי מוגדר לפי שיוך |
| User | ForumPost | 1-to-many | |
| User | DirectMessage (נשלח) | 1-to-many | |
| User | DirectMessage (התקבל) | 1-to-many | |
| User | ProfessionalQuery | 1-to-many | |
| Professional | ProfessionalQuery | 1-to-many | אופציונלי |
| Professional | Group/Sector | many-to-many | |
| User | Report | 1-to-many | על כל סוגי התוכן |
| Admin/Moderator | AuditLog | 1-to-many | |
| User | Document | 1-to-many | מסמכים מרובים |

## 3. הרשאות ותפקידים

### 3.1 תפקידים במערכת

#### Admin (מנהל)

- אחריות: ניהול כלל המערכת, אישור הרשמות, ניהול אנשי מקצוע ומבקרים
- ניגש לכל הנתונים ללא הגבלת מגזר/קבוצה (לצורכי ניהול בלבד)
- **לא יכול** לקרוא הודעות פרטיות של משתמשים (הגנת פרטיות מוחלטת)
- יכול להשעות/לבטל חשבונות, לאשר/לדחות הרשמות, לנהל קטלוג אנשי מקצוע
- מקבל התראות על בקשות הרשמה ממתינות ואירועים חריגים

#### User (משתמש)

- רואה אך ורק תוכן השייך לקבוצתו ולמגזרו
- יכול לפרסם בפורום הרלוונטי לו, לשלוח הודעות פרטיות לחברי קבוצתו
- יכול לשאול שאלות מקצועיות (ציבוריות או פרטיות)
- יכול לדווח על תוכן שאינו הולם
- **לא יכול** לראות פרטי משתמשים אחרים (שם בלבד, ללא פרטי קשר)
- **לא יכול** לגשת לתוכן של קבוצות/מגזרים אחרים

#### Professional (איש מקצוע)

- גישה לפורום המקצועי בלבד (לא לפורום הקהילתי)
- רואה שאלות מופנות אליו/לתחומו, בהתאם למגזרים וקבוצות שאליהן שויך
- יכול לענות על שאלות ציבוריות ופרטיות
- **לא רואה** מידע מזהה של השואל — שם ברמת כינוי בלבד ("אלמנה — ספרדי") אלא אם השואל בחר לחשוף שמו
- מקבל התראות מייל על שאלות חדשות

#### Moderator (מבקר)

- **מינוי:** מהנהלת העמותה בלבד — ממונה על ידי מנהל דרך ממשק הניהול; לא מתוך הקהילה
- אחריות: טיפול בדיווחים בתוך הקבוצה/מגזר שהוגדרו לו
- רואה דיווחים ממתינים + ההקשר המלא של ההודעה המדווחת
- יכול: למחוק הודעה, לבטל דיווח, להשעות משתמש (זמנית)
- **לא יכול:** לראות הודעות פרטיות, לשנות נתוני משתמש, לאשר הרשמות
- מקבל התראות מייל על דיווחים חדשים ואירועים חריגים

## 4. מנגנון סינון קבוצות ומגזרים

### 4.1 מטריצת קבוצות-מגזרים

המערכת פועלת לפי שני צירים עצמאיים. כל משתמש משויך לתא אחד בלבד:

| קבוצה \ מגזר | חסידי | ליטאי | ספרדי | כללי |
|---|---|---|---|---|
| אלמנים | תא 1.א | תא 1.ב | תא 1.ג | תא 1.ד |
| אלמנות | תא 2.א | תא 2.ב | תא 2.ג | תא 2.ד |
| יתומים | תא 3.א | תא 3.ב | תא 3.ג | תא 3.ד |
| יתומות | תא 4.א | תא 4.ב | תא 4.ג | תא 4.ד |

### 4.2 לוגיקת סינון תוכן

כל פרסום בפורום מוגבל לפי הרשאת השולח:

**משתמש רגיל — תא שלו בלבד:**
- יכול לפרסם לתאו הספציפי בלבד (קבוצה + מגזר ספציפיים)
- לא ניתן לפרסם לקבוצה שלמה, למגזר שלם, ולא ל"כולם"

**מנהל / איש מקצוע — שידור מורחב:**
- יכול לשדר לקבוצה שלמה (כל המגזרים של אותה קבוצה)
- יכול לשדר למגזר שלם (כל הקבוצות של אותו מגזר)
- פעולת שידור נרשמת ב-Audit Log

> **⛔ אין "כולם":** לא קיימת אפשרות הפצה לכלל משתמשי המערכת. אפילו מנהל אינו שולח "לכולם" — ניתן לשלוח לקבוצה ספציפית או למגזר ספציפי לכל היותר.

**מימוש:** כל שורת תוכן כוללת שדות `group_visibility` ו-`sector_visibility`. ה-API מחיל WHERE clause אוטומטי לפי פרופיל המשתמש המחובר. הגבלת סוג ההפצה נאכפת ב-middleware לפי `role`. לא ניתן לעקוף סינון זה דרך ה-API.

### 4.3 גישת מבקרים

מבקר משויך לרשימה של תאים (קבוצה+מגזר). הוא רואה דיווחים הנוגעים לתכנים בתאים שהוגדרו לאחריותו בלבד. מבקר יכול לנהל מספר תאים, אך לא כל המערכת (זאת שמורה למנהל).

## 5. מודול פורום ותקשורת

### 5.1 סוגי הודעות

| סוג | יעד | מי יכול לשלוח | מי רואה |
|---|---|---|---|
| הודעת תא | קבוצה + מגזר ספציפיים | כל משתמש פעיל | חברי התא בלבד |
| שידור לקבוצה | קבוצה שלמה (כל המגזרים) | **מנהל / איש מקצוע בלבד** | כל חברי הקבוצה |
| שידור למגזר | מגזר שלם (כל הקבוצות) | **מנהל / איש מקצוע בלבד** | חברי המגזר בכל הקבוצות |
| הודעה פרטית | משתמש ספציפי | כל משתמש פעיל | שולח + מקבל בלבד |

### 5.2 תרשים זרימה — פרסום בפורום

1. משתמש לוחץ "הודעה חדשה"
2. בוחר סוג הפצה: **תא שלי בלבד** (משתמש רגיל) — או — תא / שידור לקבוצה / שידור למגזר (מנהל / איש מקצוע בלבד)
3. כותב כותרת ותוכן (עד 5,000 תווים), מצרף קובץ אופציונלי (תמונה/PDF, עד 5MB)
4. המערכת בודקת: משתמש פעיל? | לא מושעה? | תוכן עומד במדיניות? (בדיקה אוטומטית בסיסית — סריקת מילות מפתח)
5. אם עבר: ההודעה מפורסמת, מוצפנת, עם timestamp
6. אם נכשל: הודעת שגיאה מתאימה
7. כפתור דיווח זמין מיד עם הפרסום

### 5.3 הודעות פרטיות

- משתמש מחפש נמען לפי שם בלבד בתוך **אותו תא בלבד** (קבוצה + מגזר זהים) — DM אינו חוצה קבוצות ואינו חוצה מגזרים
- הודעות מוצפנות בשרת (server-side encryption); לא נגישות למנהל ולמבקר
- **מדיניות הצפנה:** server-side encryption — ההודעות אטומות לכולם ברגיל. מבקר רואה תוכן **אך ורק** של הודעות שדווחו במפורש ע"י משתמש. זו הסכמה מרצון — לא גישה פסיבית. ממשק המשתמש יציג זאת בשקיפות מלאה.
- כפתור דיווח זמין גם בהודעות פרטיות
- **אחסון מוגבל:** עד 1,000 הודעות לשיחה, ניקוי אוטומטי לאחר 3 שנים
- **מה"ק (מנגנון הגנה קהילתי):** לאחר מספר דיווחים חוזרים על אותו שולח → הגבלת שימוש זמנית אוטומטית, לבחינת מבקר

## 6. מודול ייעוץ מקצועי

### 6.1 קטלוג אנשי מקצוע

כל איש מקצוע מקוטלג לפי:

- **תחום:** עו"ד, רואה חשבון, פסיכולוג, יועץ כלכלי, רב/דיין, רפואה, סוציאל וורקר, אחר
- **מגזרים:** חסידי/ליטאי/ספרדי/כללי (ניתן לסמן "הכל")
- **קבוצות:** אלמנים/אלמנות/יתומים/יתומות (ניתן לסמן "הכל")

דף פרופיל (גלוי למשתמש המורשה) כולל: שם, תחום, תיאור קצר, מגזרים. **אינו כולל** מייל, טלפון, פרטים מזהים (הגנת פרטיות דו-כיוונית).

### 6.2 תרשים זרימה — שאלה מקצועית

1. משתמש פותח "ייעוץ מקצועי" → רואה רשימת אנשי מקצוע הרלוונטיים לו
2. בוחר: שאלה לאיש מקצוע ספציפי / שאלה כללית לתחום
3. מגדיר: ציבורית (גלויה לכל חברי קבוצתו/מגזרו) / פרטית (לאיש המקצוע בלבד)
4. כותב את השאלה (עד 2,000 תווים)
5. המערכת שולחת התראת מייל:
   - שאלה ספציפית → מייל ישיר לאיש המקצוע הנבחר
   - שאלה כללית → מייל לכל אנשי המקצוע בתחום עם ציון "שאלה כללית — ייתכן שכבר נענתה"
6. איש המקצוע נכנס, רואה שאלות ממתינות, מגיב
7. עם קבלת תשובה — משתמש מקבל התראת push/מייל

### 6.3 ניהול תגובות ציבוריות

שאלות ציבוריות שנענו הופכות ל"ידע קהילתי" — גלויות לכל חברי אותה קבוצה/מגזר. ניתן לסמן תשובה כ"מועדפת" ע"י השואל. אנשי מקצוע יכולים להוסיף עדכון/הבהרה לתשובות קיימות.

### 6.4 הגנות על פרטיות בייעוץ

- **שאלות פרטיות:** גלויות לאיש המקצוע ולשואל בלבד
- **שם השואל:** מוצג לאיש המקצוע ברמת כינוי בלבד ("אלמנה — ספרדי") — אלא אם השואל בחר לחשוף שמו
- **מניעת ייצוא:** לא ניתן לייצא/להוריד שאלות פרטיות

## 7. מודול הגנה על משתמשים ומענה קהילתי

> **הערת גרסה:** שמות השדות בסעיף זה נוסחו מחדש בגרסה 2 בלשון רכה יותר. המשמעות הטכנית זהה לחלוטין לגרסה 1.

### 7.1 מנגנון הדיווח

- כל הודעה (פורום/שאלה/הודעה פרטית) נושאת כפתור "דיווח"
- משתמש לוחץ דיווח → בוחר סיבה: התנהגות לא הולמת / תוכן בעייתי / ספאם / אחר
- הדיווח נרשם: מזהה מדווח, מזהה מדווח-עליו, מזהה הודעה, סיבה, timestamp

**זרימת טיפול אוטומטי:**

| דיווח | פעולה אוטומטית |
|---|---|
| ראשון | התראת מייל למבקר האחראי על אותה קבוצה+מגזר |
| שני (ממשתמש שונה) | הסתרה אוטומטית של ההודעה + התראת דחיפות למבקר |
| שלישי+ | מייל חוזר למבקר (ניסיון יצירת קשר נוסף) |

מבקר מקבל התראה עם: ההקשר המלא, מספר הדיווחים, זהות המדווחים (לא זהות המדווח-עליו לצד השואל).

**החלטת מבקר:**
- **מחיקה** → הודעה נמחקת, מדווח-עליו מקבל הודעת מערכת, דיווח מסומן "מוצדק"
- **ביטול** → הודעה מוצגת מחדש, דיווח מסומן "שגוי"

### 7.2 מנגנון מעקב ואירועים חריגים

| מצב | סף | פעולה |
|---|---|---|
| מדווח-שגוי תכוף | 5+ דיווחי-שגוי ב-30 יום | התראה למבקר + מגבלת דיווח (3 ליום) |
| מדווח-עליו תכוף ומוצדק | 3+ דיווחים-מוצדקים ב-30 יום | התראה למנהל + עיון בהשעיה |
| אירוע חוזר משמעותי | 2+ אירועים-מוצדקים ב-7 ימים | השעיה אוטומטית זמנית (48ש') + התראה למנהל |

### 7.3 לוח בקרת מבקר

- רשימת דיווחים ממתינים (ממוינים לפי מספר דיווחים)
- היסטוריית דיווחים (מטופלים/מבוטלים)
- כרטיס משתמש: מספר פעמים שדווח עליו, מספר פעמים שדיווח שגוי
- אפשרות השעיה ידנית + הערת מבקר (לתיעוד)

## 8. תהליך הרשמה ואימות

### 8.1 שלבי הגשת הבקשה

1. **פרטים אישיים:** שם מלא, ת"ז/מספר דרכון, תאריך לידה (חובה: 18+ בעת ההרשמה), מגדר, סוג (אלמן/ה, יתום/ה), שאלות זיהוי שיוך (סגנון לבוש, קהילה וכד')
   > שיוך המגזר והתא הסופי נקבע על ידי **המנהל** בעת בחינת הבקשה — על בסיס המסמכים ושאלות ההרשמה. המשתמש אינו בוחר את מגזרו בצורה עצמאית.
2. **פרטי קשר:** מייל, טלפון — יאומתו ב-OTP
3. **העלאת מסמכים:** תמונת זיהוי (selfie), תעודת פטירה של בן/בת הזוג (אלמן/ה) או ההורה (יתום/ה), תעודת זהות/דרכון
4. **הצהרות:** אישור תנאי שימוש, הסכמה לעיבוד מידע, הצהרה על אמיתות המסמכים
5. **שלב המתנה:** הבקשה עוברת לתור הממתינים לאישור
   > **מייל אוטומטי מיידי:** "קיבלנו את בקשתך. הבקשה תיבדק תוך 7 ימי עסקים. נעדכן אותך בכל שינוי סטטוס."

### 8.2 תהליך האישור הכפול

**מודל Parallel (מומלץ):** שני מנהלים מקבלים התראה בו-זמנית. כל אחד בוחן ומאשר/דוחה באופן עצמאי. הרשמה מאושרת רק כאשר שני המנהלים אישרו.

**מספר מנהלים:** 5 מנהלים פעילים — נדרש אישור 2 מתוכם. הגדרה זו מבטיחה מניעת עצירת תהליך בעת היעדרות.

**SLA:** 7 ימי עסקים לאישור מלא (שני מנהלים). לאחר 7 ימים ללא אישור מלא — התראה למנהל הבכיר. מייל "קיבלנו" נשלח מיידית (ראה שלב 5 לעיל).

**מודל Sequential (חלופה):** מנהל א' בוחן ומאשר ראשון. רק לאחר אישורו, מנהל ב' מקבל התראה ובוחן.

### 8.3 כניסה חוזרת — Google OAuth

לאחר השלמת הרשמה מלאה ואישור שני מנהלים, משתמש יכול **אופציונלית** לקשר את חשבון Google לכניסות עתידיות. Google OAuth הוא **מנגנון כניסה בלבד** — אינו מחליף ואינו מקצר את תהליך ההרשמה/אימות.

**דרישות יישום (ספרינט 4):**
- שדה `google_uid` (nullable) בישות User + migration
- endpoint לקישור חשבון Google (לאחר login רגיל)
- OAuth2 callback עם בדיקת סטטוס חשבון — חשבון מושעה/מבוטל חסום גם דרך Google
- ביטול קישור אפשרי דרך הגדרות משתמש

### 8.4 מצבי ביניים ותרשים זרימה

| סטטוס | משמעות | פעולות אפשריות |
|---|---|---|
| ממתין_לאימות | ממתין לאימות מייל/טלפון | שליחת OTP מחדש |
| ממתין_לאישור | הוגשה, ממתין לשני מנהלים | מנהל: אישור/דחייה/בקשת מידע נוסף |
| אושר_חלקית | מנהל אחד אישר | ממתין למנהל שני |
| פעיל | שני מנהלים אישרו | גישה מלאה |
| נדחה | אחד/שניים דחו | הודעה + אפשרות ערעור (30 יום) |
| מושעה | מנהל/מבקר השעה | השעיה זמנית עם תאריך סיום |
| מבוטל | המשתמש ביקש מחיקה | מחיקת נתונים לפי GDPR |

## 9. אבטחה ודרישות טכניות

### 9.1 הצפנה

- **מסמכים ותמונות:** AES-256 at rest, אחסון ב-S3/Blob Storage עם presigned URLs בתוקף מוגבל (15 דקות)
- **ת"ז ופרטים מזהים:** מוצפנים ב-DB ברמת שדה (field-level encryption) עם מפתח נפרד לכל משתמש
- **הודעות פרטיות:** מוצפנות בשרת (server-side encryption); אפשרות שדרוג ל-E2E בגרסה 2
- **תעבורה:** TLS 1.3 בלבד, HSTS, HTTPS חובה
- **סיסמאות:** bcrypt עם cost factor ≥ 12

### 9.2 RBAC — ניהול הרשאות

- כל endpoint מוגן ברמת middleware עם בדיקת תפקיד + שייכות לקבוצה/מגזר
- JWT tokens עם תוקף קצר (15 דקות) + refresh token (7 ימים)
- ביטול session מיידי עם השעיה/ביטול חשבון
- עקרון הרשאות מינימליות (Least Privilege)

### 9.3 Audit Trail

- כל פעולה מנהלתית/רגישה נרשמת: מי, מה, מתי, IP
- לוגים append-only, חתומים — אינם ניתנים לעריכה
- שמירת לוגים: 7 שנים (דרישה ישראלית)
- גישה ל-Audit Log: מנהל בלבד
- **חסר בגרסה הנוכחית:** סינון לפי סוג פעולה ו-entity_type (מסומן TODO בקוד)

### 9.4 מדיניות שמירה ומחיקה

| סוג נתון | תקופת שמירה | עם מחיקת חשבון |
|---|---|---|
| הודעות פורום | 5 שנים | אנונימיזציה (לא מחיקה) |
| הודעות פרטיות | 3 שנים | מחיקה מלאה |
| שאלות מקצועיות ציבוריות | 7 שנים | אנונימיזציה |
| שאלות מקצועיות פרטיות | 5 שנים | מחיקה מלאה |
| מסמכי הרשמה | 10 שנים | מחיקה עם אישור מנהל |
| Audit Logs | 7 שנים | לא נמחקים |
| דיווחים | 5 שנים | אנונימיזציה |

### 9.5 נגישות

**תקן ישראלי 5568 / WCAG 2.1 AA** — זו חובה חוקית לפי תקנות שוויון זכויות לאנשים עם מוגבלות (2013). לפלטפורמה שפונה לאוכלוסייה מבוגרת ופגיעה — דרישת MVP.

| דרישה | ערך |
|---|---|
| ניגודיות צבעים | 4.5:1 לטקסט רגיל, 3:1 לטקסט גדול |
| ניווט מקלדת | כל אלמנט אינטראקטיבי נגיש ב-Tab |
| Focus indicator | גלוי ברור בכל מצב |
| ARIA | תיוג מלא לכל רכיב ממשק |
| היררכיית כותרות | h1→h2→h3 בסדר תקין, לא מדלגים |
| גופן מינימלי | 16px; layout לא נשבר בהגדלה ל-200% |
| שפה וכיוון | `<html lang="he" dir="rtl">` על ה-root |
| תמונות | alt text לכל תמונה משמעותית |

### 9.6 פילטרי תוכן קהילתיים

> **⚠️ דרישת פריסה קריטית:** קהל היעד העיקרי מסונן ע"י פילטרי תוכן קהילתיים. דומיין שאינו מאושר — לא נגיש לרוב המשתמשים.

**סדר הפעולות הנכון:**

> ⚠️ לא ניתן לפנות לנטפרי/אתרוג/רימון לפני שיש URL פעיל. הפנייה מתבצעת **אחרי** הפריסה לענן (ספרינט 4).

1. **פריסה לענן (ספרינט 4) → קבלת URL** — תנאי מקדים לכל הפנייה
2. **נטפרי — שלב א':** אין "רישום דומיין" — הם בוחנים את אופי האתר ומחליטים לפי תוכן ומדיניות. פנייה עם URL + תיאור מפורט של המערכת. **קריטי גם למפתחות** — שהן עצמן על נטפרי ולא יכולות לגשת לאתר ללא אישור.
3. **אתרוג ורימון — שלב ב':** לברר ישירות עם כל שירות מהו תהליך האישור שלו (רימון — ממשלתי, משרד התקשורת; אתרוג — שירות קהילתי).
4. **בדיקת Zoom/Google Meet** — לאמת שקישורי הפגישות עוברים דרך הפילטרים (לאחר אישור נטפרי)
5. **שירות מייל** — OTP, התראות ואישורים חייבים להישלח מדומיין לא חסום
6. **אין CDN חיצוניים** — כל CSS/JS/פונטים inline או self-hosted (הפילטרים לעתים חוסמים CDNs)

**פילטרים רלוונטיים:** נטפרי (הנפוץ ביותר — חובה לפיתוח), אתרוג, רימון (נתמך ע"י משרד התקשורת)

### 9.7 GDPR ופרטיות ישראלית

- **גיל מינימלי:** 18 שנים — קטינים אינם רשאים להירשם. אין אפשרות רישום אפוטרופוס עבור קטין.
- **זכות גישה:** משתמש יכול לבקש העתק של כל המידע שנשמר עליו
- **זכות מחיקה:** מחיקה תוך 30 יום מבקשה, למעט נתונים בעלי חובה חוקית
- **הסכמה מפורשת:** נדרשת בנפרד לכל מטרת עיבוד
- **DPA:** מומלץ מינוי ממונה הגנת מידע (Data Protection Officer)
- **Data Breach:** נוהל גילוי פרצה תוך 72 שעות לרשות הגנת הפרטיות

### 11.1 פתרון טכני

| פרמטר | ערך |

### 11.2 כללי הרשאות

- **מי יכול לפתוח שיחה:** איש מקצוע או מנהל בלבד
- **מינימום משתתפים:** אין מינימום נדרש — השיחה נפתחת גם עם משתתף אחד
- **הפרדה לפי קבוצה/מגזר:** כמו שאר המערכת (§4) — שיחה נגישה לחברי הקבוצה/מגזר הרלוונטי בלבד
- **הזמנה:** המשתתפים מוזמנים דרך המערכת; הקישור חד-פעמי ולא ניתן להעברה

### 11.3 הערות

- הקלטה — כבויה כברירת מחדל (מגבלת Zoom Free; ניתן להפעיל בשדרוג)
- פרטיות השיחה מבוטחת ע"י הצפנת Zoom/Meet המובנית; אין גישה לתכני השיחה מצד המערכת

סוכני AI מבוססי בסיס ידע לנושאים ספציפיים, כתוסף למודול הייעוץ המקצועי האנושי — **לא כתחליף לו.**

**Disclaimer קבוע בממשק:** "המידע הוא כללי בלבד ואינו מהווה ייעוץ מקצועי מחייב."

### 12.2 ארכיטקטורה

- בסיס ידע ייעודי לכל סוכן — מוגבל לתחומו בלבד
- מודל שפה: Claude Haiku או GPT-4o-mini (המפתחים יבחרו — שניהם זולים ומתאימים; Claude מצטיין בעברית)

### 12.3 עדכון בסיס הידע

## 16. מונחון

| מונח | הגדרה |
|---|---|
| RBAC | Role-Based Access Control — מנגנון הרשאות המבוסס על תפקיד המשתמש |
| Audit Trail | יומן פעולות בלתי ניתן לשינוי המתעד כל פעולה רגישה במערכת |
| OTP | One Time Password — קוד חד-פעמי לאימות זהות |
| AES-256 | תקן הצפנה מתקדם בגודל מפתח 256 ביט |
| GDPR | General Data Protection Regulation — תקנות הגנת מידע אירופאיות |
| JWT | JSON Web Token — אסימון אימות דיגיטלי חתום |
| E2E Encryption | End-to-End Encryption — הצפנה כך שרק השולח והמקבל יכולים לקרוא |
| ERD | Entity Relationship Diagram — מפת קשרים בין ישויות המידע |
| Presigned URL | קישור זמני ומוגבל-זמן לגישה לקובץ מאובטח באחסון ענן |
| SLA | Service Level Agreement — הסכם רמת שירות ומדדי זמן תגובה |
| מה"ק | מנגנון הגנה קהילתי — הגבלה אוטומטית זמנית לאחר דיווחים חוזרים על אותו גורם |
| Zoom API / Google Meet API | ממשקי API ליצירה וניהול פגישות וידאו — המפתחים יבחרו את הפשוט יותר לאינטגרציה |
| cold start | עיכוב בהפעלת שרת Render לאחר תקופת חוסר פעילות (מגבלת Free Tier) |
| DPA | Data Protection Officer — ממונה הגנת מידע |
| Google OAuth | פרוטוקול אימות גוגל — בפרויקט זה משמש לכניסה חוזרת בלבד, לא להרשמה |
