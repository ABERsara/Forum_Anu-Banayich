ABF-152 — יומן פעולות: תצוגה, סינון ועימוד

ABF-152 Audit Log — תצוגה + סינון + עימוד ~2.5 ימים
לפני כתיבת שורת קוד: לוודא שקיים audit_service.get_audit_log() — אם קיים, להרחיב את החתימה. אם לא, ליצור. הקונטרקט מתפרסם לצוות לפני שמישהי מתחילה לקודד.

לפני

  • GET /admin/audit-log מחזיר [] עם TODO comment
  • AuditLogComponent מציג <p>TODO</p> בלבד
  • audit_service.get_audit_log() — חתימה חלקית בלבד

אחרי

  • טבלה אמיתית: מי / מה / מתי / ישות
  • פאנל סינון, עמודות ניתנות למיון, עימוד
  • DB-level LIMIT/OFFSET — ללא full-table fetch
החלטה מתועדת — IP: IP מאוחסן מוצפן ב-DB כנדרש, אך לעולם לא מוצג ב-UI. הסיבה: מידע אישי תחת GDPR; יומן הפעולות ממלא את ייעודו המלא דרך actor_id + action_type + timestamp בלבד.

קונטרקט API (קפוא — לא לשנות)

פרמטרסוגתיאור
actor_idoptionalסינון לפי מבצע הפעולה
action_typeoptionalסוג הפעולה
entity_typeoptionalסוג הישות
date_from / date_tooptionalטווח תאריכים
sort / directiondefault: timestamp / descמיון
page / page_sizerequiredעימוד

תגובה: { items: [...], total_count, page, page_size }

Definition of Done

  • User / Moderator / Professional → 403 ברמת ה-API
  • Admin → 200 עם נתונים אמיתיים מה-DB
  • כל שילוב פילטרים מחזיר את החיתוך הנכון
  • עמוד 1 ≠ עמוד 2; total_count מדויק
  • שאילתת ה-DB מוגבלת — אין full-table fetch
  • תוצאה ריקה → הודעה ברורה על המסך

חדש — יומן פעולות: ייצוא CSV

חדש Audit Log CSV Export ~0.5 ימים | תלויה בקונטרקט ABF-152
פורמט: CSV בלבד. הקהל הוא מנהלים לא-טכניים שמשתמשים ב-Excel לצרכי ציות ועורכי דין. JSON יכול להתווסף בטיקט עתידי אם יעלה צורך טכני.

לפני

  • אין אפשרות לייצוא

אחרי

  • כפתור "ייצוא CSV" — מעביר את הפילטרים הפעילים
  • StreamingResponse עם UTF-8 BOM לתמיכה ב-Excel
  • ללא IP בייצוא

Definition of Done

  • Non-Admin → 403
  • שורות הקובץ תואמות בדיוק לתצוגה הסוננת
  • הקובץ נפתח ב-Excel ללא בעיות encoding עם עברית
  • אין full-table fetch — שאילתת ה-DB מוגבלת לשורות המתאימות

ABF-154 — כללי הפרה אוטומטית

ABF-154 Auto-violation Rules — 2 כללים אוטומטיים ~1.5 ימים

לפני

  • _check_auto_suspension() — stub ריק (pass)
  • _check_frequent_false_reporter() — stub ריק
  • שתיהן לא נקראות בשום מקום
  • עמודת is_report_restricted — לא קיימת

אחרי

  • כלל 1: 3+ דיווחים תקפים ב-7 ימים → השעיה 48 שעות
  • כלל 2: 5+ דיווחי שווא ב-30 יום → is_report_restricted
  • שתי הפונקציות מחוברות ל-decide_report()
  • דיווח ע"י משתמש מוגבל → 403
שימו לב: ABF-154 ו-ABF-113 שתיהן נוגעות ב-report_service.py. מי שלוקחת את ABF-113 צריכה לעשות rebase על ABF-154 אחרי מיזוגה, או לתאם מראש.

Definition of Done

  • 2 דיווחים תקפים ב-7 ימים — כלום לא קורה
  • 3 דיווחים תקפים ב-7 ימים — המשתמש מושעה 48 שעות
  • משתמש מושעה כבר — אין השעיה כפולה
  • 4 דיווחי שווא ב-30 יום — כלום לא קורה
  • 5 דיווחי שווא ב-30 יום — is_report_restricted = True
  • משתמש מוגבל שמנסה לדווח → 403
  • כל ההתנהגות מכוסה בטסטים עם fixtures לשליטה בזמן

ABF-113 — דיווחי DM בממשק המבקר

ABF-113 — In Review DM Reports — מבקר רואה ומחליט על הודעות פרטיות ~0 — ממתין למיזוג
הטיקט In Review — ABF-112 (ספרינט 5) בנה את צד המשתמש: כפתור דיווח, הסכמה, צילום מוצפן. ABF-113 הוא הצד של המבקר — היה מחוץ ל-scope בכוונה ונכנס עכשיו.

לפני

  • _to_report_with_content() — מחבר ForumPost בלבד
  • מבקר לא יכול לראות תוכן הודעה פרטית שדווחה
  • ממשק הדיווחים לא מבחין בין DM לפוסט

אחרי

  • מבקר רואה את ההודעה המדווחת — הצילום המוצפן בלבד
  • אין גישה לשיחה המלאה — by design
  • כל צפייה נרשמת ב-audit log

Definition of Done

  • דיווח DM מופיע ברשימה עם תווית "הודעה פרטית"
  • מבקר רואה רק ההודעה המדווחת — לא שיחה, לא metadata של שיחה
  • מבקר מחוץ לתא של הדיווח לא יכול לגשת אליו
  • כל צפייה בתוכן מוצפן נרשמת ב-audit log
  • אין רגרסיה בטיפול בדיווחי פוסט בפורום

ABF-155 Moderator Navigation + Report Detail Page ~1 יום | עצמאית

ABF-156 — Google Meet

ABF-156 Google Meet — תזמון פגישות ויועץ-תא ~5 ימים | שלב A לפני שלב B
OAuth נפרד: Google Login קיים ועובד (openid, email, profile). יצירת Google Meet דורשת אישור נוסף ל-Google Calendar API — צעד הרשאה נפרד שמשתמש רואה בפעם הראשונה שהוא יוצר פגישה.

לפני

  • אין Meeting model, אין meetings endpoint
  • אין google_meet_service
  • אין תמיכה בפוסט מסוג MEETING בפורום

אחרי

  • יועץ מתזמן פגישה עם תאריך + כותרת
  • הפגישה מופיעה בפורום כהכרזה עם "הצטרפות"
  • לחיצה על "הצטרפות" → Google Meet

שלב A — Backend (חייב למזג לפני שלב B)

  • backend/app/models/ — מודל Meeting חדש + migration
  • backend/app/services/google_meet_service.py — exchange_calendar_token + create_meeting
  • backend/app/api/v1/endpoints/meetings.py — POST + GET /api/meetings
  • backend/app/api/v1/router.py — רישום meetings router
  • backend/core/config.py + .env.example — GOOGLE_CALENDAR_SCOPE + GOOGLE_REDIRECT_URI_MEET

שלב B — Frontend (אחרי מיזוג שלב A)

  • frontend/src/app/core/services/meeting.service.ts — createMeeting + getUpcomingMeetings
  • frontend/src/app/features/forum/ — כרטיס MEETING: כותרת, תאריך/שעה, כפתור "הצטרפות"; ללא לייק, ללא תגובות
  • frontend/src/app/features/advice/ — כפתור "תזמון פגישה" ליועץ; אם Calendar לא מאושר — צעד "חיבור Google Calendar" לפני השליחה
  • frontend/src/app/app.routes.ts — route לתהליך יצירת פגישה אם נדרש

Definition of Done

  • יועץ ללא אישור Calendar → prompt להרשאה → לאחר אישור הטופס ממשיך
  • משתמש / מבקר / מנהל לא יכולים לגשת לפתיחת פגישה
  • יצירת פגישה → Meeting record ב-DB + ForumPost מסוג MEETING
  • ההכרזה גלויה לכל חברי התא ובלתי גלויה מחוצה לו
  • לחיצה על "הצטרפות" → קישור Google Meet הנכון
  • פגישה שעברה → "הצטרפות" מושבת; ההכרזה נשארת

Definition of Done — ספרינט הסיום

כל משימה

✓ endpoint חדש → schema Pydantic (request + response) קיים
✓ endpoint חדש → רשום ב-router.py
✓ route רגיש → auth dependency מוזרק
✓ component חדש → standalone: true
✓ דף חדש → lazy-loaded via loadComponent
✓ התנהגות חדשה → טסט נוסף או מעודכן
✓ אין console.log / print() בקוד
✓ אין secrets, tokens, או API keys קשיחים
סיום ספרינט 7 = המערכת מוכנה לשימוש מלא.
כל המודולים מ-SPEC.md מיושמים. אין NotImplementedError ואין stubs פתוחים. ניתן לפנות ללקוח לדמו סופי.
